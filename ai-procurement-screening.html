AI Procurement Risk Screening: From Policy Analysis to Working Prototype

A two-part project: a graduate policy analysis of a real gap in Alabama state government, followed by a working software prototype that implements it.

PythonStreamlit scikit-learnPolicy Analysis Bardach Framework
Live Demo ↗ GitHub Repo ↗

The Problem

Alabama state government has no formal, pre-purchase review process for AI and machine learning technology. Agencies can — and do — buy AI-enabled software without any structured check on how it will be used, what data it touches, or what happens when it fails.

Compounding this: vendors increasingly embed AI features into products agencies already own, often without calling attention to it. An agency may not even realize it's procuring an AI system, because the capability was added quietly to something familiar.

Part 1 — The Policy Analysis

Using Eugene Bardach's eight-step policy analysis framework, I built a statewide, two-phase proposal.

Phase 1 — Executive branch pilot. A rule-based hard gate for high-stakes AI use cases — benefits eligibility, criminal justice, child welfare, biometric or health data — routing them to mandatory full human review, no exceptions. Everything else moves through a lightweight, ML-assisted triage process that scores risk to help a small review team prioritize their queue, never to approve or deny anything automatically.

Phase 2 — Legislative extension. Scaling the same disclosure-first, human-in-the-loop framework to the rest of state government.

One design decision threads through the whole proposal: a mandatory disclosure check on every purchase request, not an opt-in one. Because vendors can embed AI into products without an agency's knowledge, a screening system that only activates when someone already recognizes "this is AI" can be silently bypassed by ignorance, not just malice. The two-question disclosure gate applies to every request regardless of whether the requester thinks AI is involved.

The proposal grounds its $200K pilot budget in a real cost-avoidance case: Michigan's MiDAS unemployment fraud detection system, which wrongly flagged tens of thousands of residents with no human review, and which the state ultimately settled for $20 million. That case makes the argument for human-in-the-loop review economically, not just ethically.

Deliverables produced: an executive verbal briefing (slide deck and full speaker script) making the case to state leadership including ROI justification; a cross-functional colleague briefing deck with a practical "how to tell if a purchase includes AI" guide for non-technical staff; and a critical reflection covering trade-offs, equity concerns, and institutional capacity constraints.

Part 2 — The Working Prototype

To make the design's core trade-off — machine learning should triage, not decide — something a reviewer could click through rather than only read about, I built it as a real Streamlit application.

Every purchase request │ ▼ Disclosure Gate (rule-based, mandatory on every request) │ AI disclosed / not sure ▼ Tier 0 Hard Gate (rule-based, NO model) ──► benefits eligibility / criminal justice / │ not a Tier 0 category child welfare / biometric / health data ▼ → ALWAYS full human review Tier 1 ML Triage (RandomForest, advisory) → Low / Medium / High, orders the queue │ ▼ Human Reviewer (dashboard) → Approve / Escalate / Request More Info

Key design decisions

The Tier 0 gate is pure rule logic — no model is ever called. This isn't a threshold on a score; it's a hard-coded exclusion, so the riskiest requests can never be quietly triaged by an algorithm.
The ML model is advisory only. Its Low/Medium/High output orders a review queue. It never appears as "approved" or "denied," and nothing in the app can auto-approve a request — every path ends with a human clicking a button.
Disclosure-first intake. Every submitted request answers a mandatory AI-disclosure question before anything else happens, closing the "vendor embedded AI without telling us" gap identified in the policy analysis.
Train/serving population matching. Because Tier 0 requests never reach the model in production, they're excluded from its training data too — the model only ever sees the population it will actually be asked to score.
Honest, lightweight explainability. Each score comes with a plain-language list of the factors that pushed it up ("vendor did not disclose testing results," "no human-in-the-loop planned"), built from feature importances rather than SHAP or LIME — a deliberate simplicity trade-off for a demo, documented as such rather than overstated.

What's in the app

Home — overview, live queue metrics, navigation. Submit a Request — disclosure gate, full intake questionnaire, instant risk score with explanation. Reviewer Dashboard — filterable queue, per-request detail with a probability breakdown chart, and reviewer actions. About This Tool — model card, methodology, and the limitations section below.

Built with Python, Streamlit, scikit-learn (RandomForestClassifier), pandas, plotly, and joblib. No external database — flat-file JSON persistence, by design, to keep the demo dependency-free.

Known limitations, stated plainly. This is a portfolio demonstration, not production software. All requests, vendors, and incident histories are synthetic; real Alabama agency names are used for realism only, and the project has no affiliation with the State of Alabama. The model is trained on roughly 600 synthetically generated rows using a hand-specified risk formula, not real procurement outcomes, and hasn't been tested for fairness or bias. These limitations are documented in-app on the About page rather than only in the README, so they travel with the tool.

Origin

This began as an assignment for my graduate program, applying Bardach's framework to a real gap in Alabama's technology procurement process. The prototype is the "what if we actually built it" follow-up — turning the two-tier governance design into working code so its central trade-offs (thin training data, vendor self-report reliability, the detection gap for embedded AI) are things a visitor can click through, not just read about.
